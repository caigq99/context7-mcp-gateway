# Security Notes

## Current secret handling

- `GATEWAY_ENCRYPTION_KEY` and `GATEWAY_TOKEN_PEPPER` must each be an independent 32-byte base64url value. Production configuration refuses to start if either is missing, rejects `GATEWAY_ADMIN_TOKEN`, and requires HTTPS DNS origin plus configured Linux.do OAuth and a default pool. Do not lose or silently rotate these values.
- Upstream Context7 API keys are encrypted with ChaCha20-Poly1305. Ciphertext is bound by associated data to the pool ID and upstream-key ID, and admin APIs only return a generated non-secret hint.
- Gateway tokens contain a public random ID plus 256 random secret bits. The database stores only an HMAC-SHA-256 digest using the independently configured pepper. Raw tokens are returned only by create/rotate and never included in listings.
- Production administrator access defaults to the environment-configured username/password pair `GATEWAY_ADMIN_USERNAME`/`GATEWAY_ADMIN_PASSWORD`. Both must be set or both omitted; setting only one is a startup configuration error. Production requires at least 12 password characters (20+ random characters recommended). Keep `.env` at mode `600`; the plaintext exists only in `.env` or the deployment secret manager. The process reads it at startup and hashes it in memory with Argon2id. Plaintext is never written to the database, logs, frontend, or audit records.
- Password login returns a uniform `401 invalid_admin_credentials` for bad credentials; repeated failures are rate-limited and return `429` with `Retry-After`. Password sessions are bound to a version of the current username/password configuration, so changing `GATEWAY_ADMIN_PASSWORD` (or the username) and restarting invalidates existing password sessions. Keep reverse-proxy login rate limiting as defense in depth.
- Passkeys are optional credentials bound from Settings after password login. Password login remains available after a Passkey is bound. The last Passkey may be removed while password login is enabled; the old last-passkey protection remains only when both password variables are omitted (passkey-only mode).
- Passkey login uses an isolated WebAuthn ceremony and an HttpOnly, Secure, SameSite cookie. One-time initial/recovery enrollment codes are generated by the host CLI only for passkey-only initial setup or recovery. The bearer admin token is limited to development/test and is never accepted in production.
- OAuth login binds a one-time state cookie and a PKCE S256 challenge to a pepper-derived verifier; registration is closed by default and active sessions are revoked on logout/account disable.
- Cookie-authenticated mutations require a same-origin request and JSON content type when a body exists. Password and Passkey authentication mutations check the exact configured origin. Responses set anti-framing/CSP/security headers and API responses are marked `no-store`.
- Gateway tokens may be scoped to MCP and/or the Context7 read façade and may have a server-set expiry; the scope and expiry are rechecked before each proxy request.
- Redirects are disabled on the upstream HTTP client. Clients cannot choose the upstream host or arbitrary path. Upstream API keys are always placed by the server into the upstream Authorization header.

## Logging and usage retention

Trace spans include only HTTP method and URL path, not query string. Usage records include user/token/pool/key IDs, operation, request ID, response status and duration; raw queries, request bodies, response bodies, cookies and Authorization values are excluded. Keep reverse proxy access logging configured to omit query strings and sensitive headers as well.

## Remaining production/release checks

- The operator declares that they maintain the upstream keys and are responsible for their intended use; the repository does not verify upstream contractual permissions. The declaration is recorded in [`phase0-operator-record.md`](phase0-operator-record.md) and is not a blocking software gate. Registration remains closed by default and can be opened only when the configured default pool has an eligible active key and the OAuth, encryption and pepper configuration prerequisites are met.
- Rebuild the verified image on the deployment host and repeat backup/restore against the operator-controlled production volume.
- Exercise administrator password bootstrap, password rotation/session invalidation, optional Passkey binding, and repeated-failure `429` behavior against the target deployment.
- Exercise the upstream `401`, `403`, `429`, `5xx`, key revocation and retry behavior with a controlled/mock upstream, and test legacy MCP session resume separately; current live smoke coverage proves the successful REST and standard MCP tool flows only.
- Key sharing and pool operation are the operator's declared responsibility within the account/Teamspace and user scope they intend. Never rotate keys to evade upstream rate limits or access controls. Upstream `401` marks a key invalid, `403` marks the key `permission_error` and disables its pool pending review, and `429` cools the pool using `Retry-After`; these responses must never be bypassed by selecting another key.
- This build has not had an independent security review. Deploy behind TLS, restrict administrative network access, rotate secrets only through a planned migration, keep payment disabled unless an approved provider is implemented, and never place real credentials in source, logs, tests or screenshots.

## Incident response basics

1. Disable the affected upstream key or the whole pool in the admin API.
2. Revoke affected Gateway Keys, rotate `GATEWAY_ADMIN_PASSWORD` (which invalidates password sessions), and remove affected administrator Passkeys if exposed.
3. Preserve the database and logs for investigation; logs should not contain key material or search content.
4. Replace encryption/pepper secrets only with a documented re-encryption/token-revocation migration, because changing either key makes stored credentials unusable.
